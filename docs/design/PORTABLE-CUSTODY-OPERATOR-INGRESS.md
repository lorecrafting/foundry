## Why the present entry cannot authenticate an operator

`Gateway.protected_command/4` checks only equality with the per-Gateway `protected_capability`, then passes **caller-supplied** `actor_id` to `ProtectedPrimitives.execute`; `atomic_bundle/4` has the same capability/actor shape. Neither knows the caller's OS UID or endpoint. `ManualLane.Server.open/2` creates that capability, passes it to Gateway and returns it, Gateway PID and path from public `context/0` to in-BEAM callers. `ManualLane.CLI.context/1` calls it. `Backend.admit/3` writes controller ticket admission as `@operator`, `allow_scope` calls `Replay.root/4` with that string, and `Replay.root/4` forwards its actor to Gateway. `Replay.submit/3` likewise forwards a supplied actor in both the Gateway argument and envelope. A manual `--principal` is a string, not an authenticated peer. `bin/foundry` escapes argv into inert data for `Foundry.CLI.RPC.run/1`, but invokes release **general** `rpc` evaluation; the wrapper's lane-only decoder cannot restrict direct release RPC/evaluation. `bin/foundry-lane` lets environment choose release/node/repo/policy/runtime root and `Application.startup_mode/0` accepts `FOUNDRY_MANUAL_LANE` or app config. `rel/vm.args` does not disable distribution. None of these is a protected operator credential. Same-UID unrestricted code can use the manual lane or its general RPC to request the context and borrow its capability. Adding `admit_packet_contract` to the existing general protected-command vocabulary, or an `if actor_id == "operator"` check, would turn that borrowed capability into operator admission. Manual `ticket_admitted` and policy scope additions remain useful manual-lane records, **not** protected spec/contract provenance.

## Smallest new boundary and Core interface

**Choice: retain the existing per-Gateway internal capability, but only in a distinct, administrator-installed, service-owned OS process with a different private store and a closed, non-evaluating socket endpoint.** A new root-only bearer capability would add no protection against an unrestricted caller sharing its BEAM or service UID. It is **not sufficient in today's manual-lane process**; do not copy its capability or `Server.context/0` into the service, attach a socket to that process, or share its store. If the separate host/process/no-eval boundary or peer credentials cannot be implemented and tested, stop before productive Core mutation and seek independent review of a different root interface; no fallback to a caller-supplied UID, token, actor or config switch. Trusted administrator/root and the installed service executable remain in the trusted computing base, not agents.

A root-owned fixed service definition and executable, service-only state and bare repository, and a separate operator account implement the custody design. No agent, candidate code, plugin, check worker or same-UID unrestricted process may run as service or operator. A **fixed installed** admission-enabled service identity and store identity are checked at boot and on reopen; default for all other Gateway instances, including the ordinary manual lane, is `disabled`. An env var, CLI flag, config file in an agent-writable path or request field cannot enable or retarget it. The protected root persists the installation/admission mode and enrolled UID→principal/opaque role/project mapping with immutable UID binding, revocation generation and policy revisions; service revalidates installed owner/path/release/mode and protected root history before readiness. Enabling or changing installed service mode is administrator/operator maintenance with separate review, not a lane command or agent-accessible configuration. Mode is an additional Core guard on the *new* protected admission and packet-result/producer-seal routes, **not** evidence of peer identity by itself; existing manual-lane ordinary issue/submit continues without those new protected guarantees.

The socket listener verifies administrator-owned parent/socket identity, accepted connection peer UID (macOS `getpeereid`, Linux `SO_PEERCRED`) and service endpoint identity; clients verify the expected service peer UID and canonical protected endpoint before sending sensitive requests. The protected *maintenance entitlement* for the dedicated operator account is not a workflow role label; Core compares that fixed entitlement and opaque admitted workflow labels separately, never `developer`/`reviewer` strings as admission authority. Reject aliases/symlinks and changed inode/owner/mode. The service does not inherit a listener or connected FD from the manual lane or a client; it binds its own protected listener and closes accepted connections on restart. Connections accepted before the service generation changes cannot authorize a new call. Check credentials at accept, but read current protected enrollment/revocation/project/role/assignment **on every call**, including result reads on an existing connection. A group only permits connection. No caller-supplied actor, role, UID, project authorization, socket path or policy revision is accepted as provenance. A project ID in the request is a target to compare with protected enrollment, never an authority selector. One UID is bound to one principal/role for its lifetime; retiring it is permanent, never reassign it to another principal/role. An operator-only enrollment/maintenance path must itself use the verified separate operator peer and protected CAS; bootstrap of the initial operator mapping is a documented administrator-owned installation step, not self-enrollment over the socket.

Expose a closed versioned **operator-admission** operation (not `protected_command`, `atomic_bundle`, SQL, eval or arbitrary root command) on that socket, only to the currently enrolled operator with current project maintenance permission. Its bounded input is the canonical finite contract and immutable ticket/attempt spec from the reviewed designs, plus request ID and expected revisions. Validate schema/version/closed keys, opaque role entries, fixed modes and endpoint-authorized return verbs, unique preselected consuming entry and policy/check-set compatibility; reject arbitrary callbacks, paths, wildcard or a workflow role literal in Core. The trusted ingress passes a typed **peer-derived** UID, pinned service installation identity, connection generation, request identity and target to a dedicated Core admission command. Only installed trusted service code may construct this internal context; a caller cannot submit it over the socket. The per-instance Gateway capability authenticates this trusted process boundary, not the operator. If any general RPC/BEAM eval or untrusted module can invoke that code inside the service, stop instead of treating a context tag as proof. Inside one protected transaction Core independently reloads and CAS-checks current enrollment, revocation, project permission, installation/mode, policy and contract/spec revisions/absence keys; compares the peer-bound intent and canonical complete request; writes immutable admission/history and one durable result, or refuses all. The generic Gateway capability remains an internal transport to this *typed guarded command*, never the admission authorization predicate. Ordinary `protected_command`/`atomic_bundle` and all current manual-lane commands must refuse productive contract/spec admission when disabled, even if their actor is `operator`, and cannot write or import equivalent authenticated history. Productive packet issue/seal must require this immutable admission and same installation/store provenance; no old manual-lane ticket, policy seed, controller spec, or unreviewed backfill satisfies it. The current manual lane continues to admit/submit its ordinary tickets in its own store, without creating a protected packet result.

For an existing request ID, authorize **current** peer enrollment, revocation, project and outcome-read first; then compare authenticated original UID/principal/project, full canonical request (including old expected revisions) and admission result. Return the same result without rerunning mutation CAS. Altered bytes, sibling UID, a new ID for the same target or a different installation/store identity refuse; a revoked UID cannot recover cached bytes. The same installed service after a clean reopen has a new *connection* generation but returns the original result to a currently authorized peer on a newly authenticated connection. For a new ID recheck current assignment and every admission read-set key. Reopen reconstructs installation identity, authenticated original intent, immutable contract/spec/policy history and result, and fences missing/conflicting snapshots; no policy/env switch, claim consumption or restart may convert a manual record into protected admission. The atomic packet-result/seal read-set and historical recovery remain owned by the reviewed packet designs, not a second store or formatter here.

## Operator-client FD custody (Q26)

**Operator decision Q26 for this newly admitted design:** a trusted operator who **deliberately transfers a live connected FD** delegates that connection's authority; this is outside the restricted-hostile-agent model. It is **not a server-side refusal**. `getpeereid`/`SO_PEERCRED` report the connecting operator's credentials, not the identity of a later holder or message writer. An accidental inheritance, duplicate or receipt by an untrusted agent is in scope and must be prevented. The topology prevents *acquisition*, not individual messages from a holder already possessing an operator-connected stream. No second token, `FD_CLOEXEC`, generation or per-call enrollment check repairs a same-generation, non-revoked FD transfer.

The administrator installs one **root-owned fixed operator-only executable** and provisions a dedicated **non-admin operator OS login/account** separate from service, manual lane, developer, reviewer, candidate and tool UIDs. This is an exceptional human operator policy/contract/spec admission, **not** Q24's routine REVIEW verdict or ordinary accepted-ref PROMOTION: those stay scoped agent attestation and standing-policy exact-ref CAS without a human click each time. This login is not authority for autonomous agent-proposed ordinary new-ticket admission. That would need its own finite standing authorization rule, input provenance, acceptance and independent review. A human operator must actually inspect and authorize each exceptional body here.

**Selected installed input/login channel on both macOS and Linux:** administrator-provisioned OpenSSH `sshd` authenticates a dedicated operator public key from a **root-owned** authorized-keys path; its private key lives only in an operator-controlled trusted workstation/session, never a developer filesystem, agent, forwarded SSH agent or project tool. A root-owned `Match User` sshd configuration forces the same literal absolute client command for **every** authentication method/channel (including supplied remote command, subsystem/SFTP and reconnection), denies password/keyboard-interactive/other keys, disables TCP/agent/X11/Unix-socket forwarding and user rc/environment, and permits a PTY **only** for this forced interactive command. No developer can edit the sshd configuration, account shell, key list, home or client binary. Set the account's installed login shell to a root-owned noninteractive POSIX shell; sshd's forced-command shell `-c` executes only the literal `exec /root-owned/path/to/operator-client` and is replaced **before** any service connect. Verify no shell startup hook or inherited environment/FD survives to the client; do not rely on shell quoting of `SSH_ORIGINAL_COMMAND`. Never execute that variable or use a wrapper that interprets it. No unrestricted shell, plugin, helper, manual RPC, agent or candidate code may run as this UID, and no alternate SSH/login/launchd/systemd/sudo/su path may start a client or general program under it. On macOS the administrator installs/enables the host's Remote Login/OpenSSH service and checks effective `sshd -T -C user=...,host=...,addr=...` configuration and launchd/account policy; on Linux do the equivalent for systemd/sshd and PAM/account/PTY policy. If this exact forced-login mechanism, root-owned shell/config/key custody, and absence of another UID-switch/login path cannot be proved on a real host, disable admission there. Initial key enrollment, operator UID→principal mapping and service installation are separately authorized administrator/root bootstrap through owned configuration and protected initial state, **not** an operator socket self-enrollment or an agent-requested launch.

An authenticated SSH connection is the *OS operator login/session* selecting the client, not a root job started on an untrusted trigger. The fixed client opens its own controlling `/dev/tty` with no-follow semantics (not fd 0, argv, `SSH_ORIGINAL_COMMAND`, stdin redirection, queue, file, socket input from a helper, or mutable symlink) and verifies it is the foreground PTY in its own session with expected operator ownership, character-device identity and bounded canonical terminal settings; refuse missing/redirected/non-PTY sessions or truncated lines. Bound each canonical line and total multiline request before parsing. Disable terminal-generated injection routes (including Linux `TIOCSTI` via effective host policy and macOS equivalent debugger/PTY controls), and verify no hostile UID can open/write the operator PTY or control the SSH channel. Read a bounded canonical request interactively on that PTY with explicit length/UTF-8/closed-schema and duplicate-key rejection. The client derives/validates canonical complete bytes **once** before connect: installation/service identity, project, operation, request ID, complete finite contract/spec body, origin (the authenticated operator-login session and enrolled peer UID, not an asserted role), target and all expected revisions. Display the **entire** canonical project, operation, body and revisions (not only a digest or truncated preview) on that same PTY and require an explicit trusted operator confirmation over it. Refuse a display larger than the configured readable bound, timeout, disconnect, partial input, changed request, loss of foreground PTY or mismatch; no implicit approval, externally provided confirmation token or hidden fields. Freeze those exact bytes in client memory across retries within one login session. After client exit or service restart, the operator may use an authorized result-by-ID read or re-enter and confirm the original complete request ID/body/revisions in a fresh trusted login; the service compares that re-entered canonical request against durable original intent before returning the historical result. Never reload a candidate file or reconstruct from mutable lane state; a changed re-entry refuses without mutation. The service derives original UID/session-independent peer authority from the accepted socket credentials and checks the complete request against its durable authenticated intent; the displayed login origin is audit provenance, **not** a replacement for OS peer authentication or the human's authorization. Audit request ID, peer UID, login channel/session metadata, canonical body digest and outcome in protected history without claiming a digest alone authenticates input. A committed lost reply is recovered only by the original still-authorized operator's identical request/result read; otherwise hold unknown and seek operator reconciliation.

**Limit of the selected primitive:** OpenSSH authenticates the operator credential/channel, and PTY foreground/ownership excludes an unrelated restricted UID on the installed hosts; a PTY does **not** cryptographically prove a physical finger typed each byte. SSH client-side input can itself be piped by whoever possesses the trusted operator key/session; a compromised operator workstation, deliberately delegated key/session or trusted operator submitting hostile bytes delegates operator authority and is outside the restricted-agent model, just as deliberate FD transfer is. Confirmation is a safeguard against accidental substitution, not independent authentication. An agent-writable workstation input, shared operator key, unproven PTY injection policy, same-UID unrestricted program or generic SSH channel makes the premise false: stop rather than label a prompt or TTY trusted. Installation inspection and macOS/Linux hostile probes, not this design's words, gate enablement.

**Process tree and ownership:** operator-authenticated sshd forced-login session → shell `exec` before connect → one pinned operator-client process under operator UID → no descendants while an operator connection exists. The client starts with no authority FD, opens the canonical service socket itself, verifies the endpoint and service peer, sends one bounded request, reads its bounded result and **closes the FD before exit**. It must not fork, spawn, exec, run hooks or launch helpers between connect and close; any necessary trusted launcher completes its fork/exec **before** the operator connection opens. No generic client adapter or same-UID unrestricted shell is allowed. The client never sends `SCM_RIGHTS`, never places the FD in an IPC channel/shared descriptor table, never accepts an untrusted FD sender, and exposes no process-control endpoint that can request a fork or FD transfer. Set `FD_CLOEXEC` on both sides as defense in depth only; it does not prevent fork or descriptor passing. The service owns the accepted peer FD solely in its private process; it never passes accepted FDs to workers or an untrusted BEAM, nor forks/execs candidate code. The manual-lane RPC process has only its own unrelated connection/store. A restricted developer can create its **own** socket connection (identified as developer) but cannot read the operator process's descriptor table, fork from it, receive a sent FD from it, access a privileged debugger or run code under its UID. Therefore no hostile process acquires a live operator-connected FD without trusted-client cooperation under this precisely bounded launch topology; this is not a property of peer credentials alone.

If real installed macOS/Linux inspection finds **any** supported client, extension, helper, process or tool route that runs under operator UID or can fork, duplicate, inspect, inherit or transfer that FD to untrusted code, refuse enablement; obtain a separately reviewed feasible per-message sender-credential transport instead. Do not relabel such a path deliberate operator transfer, rely on CLOEXEC or substitute a bearer token. The separate service/store/socket, current enrollment and Core CAS below remain necessary even when the client topology holds.

## Every ingress and adversarial cut

| Route or attack | Required refusal / separation |
|---|---|
| Manual `bin/foundry lane` and `Backend.admit`, `Replay.root/submit`, `Server.context` and its Gateway | Existing manual operations continue only on manual store; no productive protected contract/spec command, regardless of `--principal operator`, same UID or copied manual capability. Cross-Gateway capability differs and protected mode defaults off. |
| Direct release `rpc`/`eval`, cookie/node attach, remote BEAM call, CLI.RPC wrapper, MCP/client adapter | Protected service has **no distribution, eval, general RPC, cookie exposure or dispatch of Gateway/context**. Manual release may retain RPC for its disjoint nonproductive store; neither wrapper parsing nor keeping a capability secret inside that BEAM is relied on. Adapters may carry only bounded data over the protected socket. |
| Direct `Gateway.protected_command`, `atomic_bundle`, query, backup/maintenance or local SQL/ref/path access from another process | No BEAM transport to service; OS mode/ownership and service-only UID deny protected store, WAL, owner marker, policy, backup destination and bare ref. No generic privileged operation or server-side path field on socket. An agent invoking a similarly named module in its own BEAM owns no protected Gateway. |
| Same-UID manual-lane user forges operator actor/UID/role, uses candidate-controlled project/config/env, alternate release/node/store/socket path or symlink endpoint | Service rejects unknown/nonoperator peer and identity/path substitution; fixed root-owned service definition/release and protected installation/policy history cannot be selected by client env. Client verifies service endpoint before sensitive transmission; changed service installation fails closed. Same UID as operator/service is **not** isolated: installation must exclude it, or stop. |
| Agent invokes ssh/forced client, forges a valid contract/spec body, changes `SSH_ORIGINAL_COMMAND`, pipes client stdin/argv/file or races an approved display | Only separately authenticated operator SSH key/session may start the fixed client; require its foreground session PTY, ignore stdin/argv/command and refuse developer key, no PTY, alternate endpoint or UID switch. Client constructs/displays/confirms complete canonical body and revisions once, then sends frozen bytes; service binds peer-derived original intent and current protected authorization. An untrusted trigger or substitution path disables admission, even when schema and FD checks pass. |
| Operator FD acquisition, pre-revocation connection, reused UID, replaced listener or restart | The fixed client and service never give their FDs to hostile processes (topology above); a developer-connected inherited FD still has developer credentials and refuses. A deliberately transferred live operator FD **would authorize its holder while the operator is enrolled and the generation is current** (Q26 trusted-cooperation exception), not refuse at the server. Restart closes old-generation connections; current protected enrollment/revocation is reloaded on **every** read/write, including old connections and result reads. Retired UID reassignment refuses. A manually inherited listener cannot authorize admission: only the installed service binds/handles its listener. |
| Crash before commit, committed reply lost, policy/spec race or missing historical snapshot | Atomic all-or-nothing admission/result; exact authorized retry reads original bytes after restart, no second admission; changed content/revision on same ID or stale **new** request refuses. Reopen validates history before readiness or fences productive routes; unknown stays held, no synthesized operator provenance. |

Administrator-provisioned **real macOS and Linux operator-input tests** (unrun future gates): install actual distinct operator/developer/service UIDs and root-owned sshd forced command, shell, key list and client. Inspect effective sshd/launchd or systemd/PAM/PTY configurations, trust-store and workstation key isolation. From a restricted developer/tool UID try SSH without the operator key, direct executable execution, ssh remote command/subsystem, request to start a root launcher, sudo/su/alternate service trigger and same-UID route; none may produce an operator-peer admission. Try schema-valid malicious contract/spec bytes via stdin pipe/file, argv, `SSH_ORIGINAL_COMMAND`, writable queue, replacement key/config/binary/symlink/helper and PTY injection/debug/FD acquisition; no body may enter without the authenticated operator's visible complete confirmation. Race approved-vs-sent body, project, operation, origin and old/new expected revisions; exact mismatch refuses. Positive: an actual trusted operator login reads the bounded request, sees the full canonical body/project/revisions, confirms once, and admits a useful finite contract/spec; authorized exact-result read and lost committed reply over a new session after two ready reopens return original bytes once. Developer/sibling/revoked read, same ID changed body/revision/project, fresh ID/same target, stale first-write CAS and changed policy refuse. Scratch red controls independently remove SSH forced-command/key segregation or inject a malicious-but-valid post-display body (each must make an authorization/body assertion fail **while FD checks still pass**); independently skip current read authorization/restart history and observe failure. A host where an unauthenticated process can write the session PTY or client input cannot pass; no synthetic-UID, one-host, unrun test counts as evidence.

Administrator-provisioned **real macOS and Linux** tests must run **as separate actual UIDs**, with the installed fixed client and service, and cover these distinct FD cuts (no tests are claimed here): (1) with the operator client holding a current connected FD, restricted developer tries Linux `/proc/<pid>/fd`, `pidfd_getfd` and `ptrace` (with its actual procfs/Yama/namespace policy), and macOS `task_for_pid`/Mach task-port/debug access and descriptor inspection (`lsof`/`proc_pidfdinfo` where available); it cannot call `dup` on a foreign FD unless one of these paths or a handoff first succeeds. Deny acquisition and verify the operator/client FD inventory, while an operator-client admission succeeds on that connection. Scratch red control: deliberately expose an untrusted same-UID executable/debug entitlement in an isolated fixture; detection must block enablement, not claim a server refusal. (2) Try a hostile fork-before-exec descendant and inheritance/`dup` of an operator FD: the actual client has **no fork after connect** and sshd forks and the forced-command shell execs before connect, so there is no such descendant; inventory child PIDs and open FDs during the request. Scratch red: inject a fork/exec after connect into the test client (including before exec with CLOEXEC set); detection must fail the topology check. (3) Have a hostile distinct-UID receiver request `SCM_RIGHTS` through every supported IPC/client/plugin path while the operator FD is live; no sender or exposed channel exists. Scratch red: add an isolated sender that passes the live FD; the receiver can then act while enrollment remains valid, so the topology acceptance **must fail**, not expect peer-credential rejection. Test a developer's own FD separately: it cannot authenticate as operator. (4) Revoke operator while an already connected request is pending and try both mutation and original-result read, then restart service, reconnect, and try an old-generation FD and a fresh unauthorized request: all refuse under current enrollment/generation. Scratch red: skip per-call enrollment or generation check independently and watch each refusal fail. (5) With enrolled operator, admit a real finite contract/spec through the fixed client, lose a committed reply, retry exact original request on a new connection across two ready reopens; get identical durable result once, while changed bytes, new ID/same target, altered revision, stale CAS and sibling developer UID refuse. Scratch red: remove result-history/restart check or authorization CAS separately; useful positive and refusal/reopen assertions must detect the fault. A dedicated fixture can intentionally transfer a live FD **only as a counterexample**, never count this as a protected refusal or run it against productive state.

Administrator-provisioned **real macOS and Linux** tests must cover installed service identity and separate operator/developer/manual UIDs, protected paths/ref/socket and no RPC; hostile agent and same-UID manual actor/role/UID claims; changed env/path/endpoint and symlink; inherited socket and copied request; live revocation including cached result on old connection; useful authorized operator contract/spec admission and developer original packet/seal; race/lost-reply/restart twice; and a distinct scratch red control for each critical mode, peer, enrollment, endpoint, CAS and restart guard. Verify listener inventory, operator FD/tool segregation, installed sshd forced-login definition plus service launchd/systemd definition, initial bootstrap and recovery. Synthetic UID fixtures or CI on one UID prove only logic, **not** installed custody. The Q25 FOUNDATION → CANDIDATE → REVIEW-BROKER → CUSTODY-CLOSURE → ACCEPTANCE order and Q24 isolated agent attestor are unchanged. Nonempty check schema and terminal non-start still require separate approval. No host evidence or implementation is claimed by this design.
