## Smallest privileged shape

The operator admits one immutable, versioned **finite packet contract** per project through the protected maintenance/admission boundary. An admission is an authenticated, append-only record with project, contract ID/revision, canonical bytes/digest, packet schema version and a closed map from opaque role labels to entries. Exactly one entry per label; no wildcard, default, aliases, implicit predecessor, caller override or change in place. A v1 entry has exactly `mode` (`no_candidate` or `frozen_candidate_all_producers`), `producer_roles` (empty for the first mode; nonempty, unique, ordered canonical labels for the second), `return_command` (one token from the installed finite command vocabulary), and `packet_schema_version=1`. Admission verifies that every producer label is an admitted role, that the role/command pair is admitted for this project's authenticated command endpoint (a packet cannot grant a new command), and that each declared producer role is permitted to produce for the consuming role. The **operator**, not a controller, chooses and reviews those entries and policy revisions. The reference lane admission has the opaque keys `developer` → `(no_candidate, [], submit, 1)` and `reviewer` → `(frozen_candidate_all_producers, [developer], review, 1)`; these strings are data in the admitted record, never new literals/sites in Core. Unknown labels, modes, commands, versions, duplicate JSON keys, extra entry fields or a command without an authorized endpoint refuse admission or issue. An effect's authenticated opaque role selects its own packet entry, but never selects the attempt's *future consuming* entry. Before any producer effect or claim, a protected operator-admitted ticket/attempt spec snapshot must name exactly one consuming-entry key and this exact contract ID/revision. Core loads that entry, requires `frozen_candidate_all_producers`, checks each producer effect's role belongs to its admitted producer-role set, and later requires the reviewer/consumer effect's role equal that selected key. Candidate-producing tickets require this single admitted selection. An explicitly admitted no-consumer policy may permit unrelated non-candidate work, but cannot issue a candidate-producing packet, submit or seal a candidate; absent/implicit selection is not that policy. Multiple keys, ambiguous revisions, an incompatible producer role, or an unselected consumer refuse. Neither a request nor a domain projection may supply/override the key. Caller-supplied mode, producer selector, binding list, callback, template, path expression or DSL are forbidden. No runtime formatter runs in Core. The contract is privileged policy data, not a new role-specific Core API: Core has only two fixed generic predicates and one closed packet schema. A revision changes only newly admitted attempts; this v1 has no compatible migration of an existing selection/seal. New policy or contract revision that conflicts with the attempt's pinned admission refuses new productive issue; a new attempt with fresh operator admission is required. Old response bytes retain their historical revision. No contract admission is itself an execution permission.

For productive issue the fixed verifier reconstructs **every field** of the closed v1 packet, encodes one canonical response, and compares the entire proposed response byte-for-byte (or emits it itself). Exact top-level keys: `schema_version`, `packet_id`, `role`, `ticket_id`, `attempt_id`, `execution_id`, `effect_id`, `request_id`, `claim_id`, `writer_epoch`, `issuer`, `base_revision`, `base_ref`, `title`, `spec_revision_id`, `scope`, `acceptance_criteria`, `checks`, `candidate`, `independence`, `return`. No omitted, extra or duplicate keys at any depth. Schema version is 1; packet ID equals execution ID. Role, ticket/attempt/execution/effect/request/claim IDs, epoch and issuer come from the authenticated original intent, staged protected issue/claim/effect and matching domain execution. Base revision/ref, title, spec revision ID and ordered scope/criteria come from that immutable **operator-admitted spec snapshot**, including its unique consuming-entry key/contract revision, for that ticket/attempt, with the domain ticket/spec required to equal it, not from a free kernel projection or packet request. Today's `Backend.admit/3` does not create that protected admission; missing authenticated history refuses even the first producer issue. `checks` is exactly `{"policy_empty":true}` only when the pinned historical protected policy's required check set is actually empty; nonempty/unknown sets refuse v1 rather than print empty (a future nonempty representation needs a separately admitted schema). `independence` has exactly `policy_id`, `policy_revision`, `independent_of_roles`, `excluded_principals`: first three come from the complete historical protected policy entry for the issued role, including ordered role labels. `return` has exactly `command` from the sealed entry and `ticket_id` from the effect. In no-candidate mode `candidate=null` and exclusions `[]`. In all-producers mode `candidate` has exactly `candidate_id` and `producer_execution_ids` from the frozen binding below; exclusions are the sorted unique **full issuer set** of precisely those producer effects. Lists are canonical (producer IDs sorted unique; exclusions sorted unique); reject missing, extra, repeated or reordered values. Historical policy and contract content are checked by revision and authenticated admission, not by present policy or a packet's digest. The issued role cannot select its own check set, excluded issuers or return verb.

## Producer seal before Git import

The authoritative **membership** is a protected, attempt-scoped seal, not a list in `artifact_frozen`, Git history, a candidate-supplied manifest, or a query of the mutable active attempt. Require one authenticated submission through an issued claim, matching its original request/epoch/effect/execution and ticket/attempt. The submission's commit/object name and artifact bytes are merely **UNVERIFIED** inputs. Under one protected transaction, Core enumerates *all* protected effect rows for that exact ticket/attempt whose role is in the **spec-selected** consuming entry's `producer_roles`, including previous retries/non-starts; checks each effect's original authenticated issuer and unique execution, its claim/epoch if claimed (or independently proved pre-claim non-start), predecessor and matching domain execution/role/attempt (bijection, with no unmatched domain producer execution or protected producer effect), and the submitting effect's issued claim and authenticated submitting actor. An unclaimed effect without proved non-start or a possible outstanding producer blocks the seal. Do not infer membership from the current active attempt, only successful receipts, or a caller's selected subset. Require at least the submitting execution, its role in the producer-role set, a valid chain, complete protected/domain history and no other unsettled productive producer capable of submitting a competing candidate. Missing claim, ambiguous duplicate execution, inconsistent inbox actor/issuer attribution, conflicting submission, missing admitted spec, or incomplete history refuses, never silently filters a row. The packet exclusion set is all these effects' **authenticated issuers**, conservatively including prior failed producers; preserve their inbox actors separately for protected independence, whose historical pairings may be stricter. Submission issuer attribution is rooted in the peer-authenticated claim (under installed custody), not in a Git author string. Before that authentication is installed, no claim of hostile-caller producer proof is permitted.

Core allocates a unique opaque candidate **binding ID** and atomically seals `(project, ticket, attempt, admitted spec revision/content and selected consuming-entry key, policy ID/revision/content, packet contract ID/revision/content, submitting claim/effect/execution/issuer, complete ordered producer execution/effect/issuer triples, attempt producer-set generation and append-only seal-cut sequence, submission request ID/digest, retained unverified submission bytes and object reference/digest)` with the authenticated submission and domain submission event. This record is immutable. Prevent subsequent producer-effect creation or another candidate submission for that attempt after seal; corrections use a new attempt and a new seal. A non-submission or failed transaction seals nothing. The fixed verifier constructs the membership set by its own exhaustive query and records its count/generation, not by checking only the proposed triples. A matching authenticated domain event is required but is not sufficient authority: Core verifies its exact identity/spec/execution linkage against root facts. Core does not certify source bytes, scope, ancestry, hooks or checks here.

Later **ML-PG-CANDIDATE** imports exactly the retained submission bytes under its own independent Git/object/scope/check verification and atomically binds its actual frozen candidate ID, repository/object format, base, commit/tree and trusted import receipt to this exact immutable seal ID and submission digest, with a unique one-to-one relation. It rejects an alternative seal, changed bytes, mismatched base/spec/attempt or double binding. A domain `artifact_frozen` proposal may refer only to that exact bound ID; a protected reviewer issue requires that binding and matching domain freeze, not merely the projection's candidate ID. This is a two-phase authority split: a seal proves *who was involved and what submission was named*, an import proves *what Git object was frozen*; check receipts require the later check authority. Neither phase alone establishes the other. Candidate import can use the seal API without already issuing/recovering a reviewer packet. [Q25's reviewed live order](../REPAIR-PLAN.md#portable-milestone-tickets-in-dependency-order) resolves the former *ticket-acceptance* cycle, not the unimplemented packet protocol: (1) separately admitted ML-PG-CUSTODY-FOUNDATION proves actual isolated operator/developer peers, protected store/ref denial, authenticated spec/contract and submission-time producer seal, original developer packet/retry and restart positives, sibling/revocation negatives and unresolved-claim holds; **no reviewer packet, decision, acceptance or promotion**; (2) ML-PG-CANDIDATE independently imports/validates those retained unverified bytes and binds verified Git/check receipts to the seal, with a legitimate positive that needs no reviewer; (3) ML-PG-REVIEW-BROKER, a distinct-UID pinned **no-execution** attestor authority, issues the reviewer packet only after verified import and trusted checks and proves a real **agent** reviewer makes one scoped exact-candidate policy-listed positive decision, while its candidate-executing tools cannot act as attestor; (4) ML-PG-CUSTODY-CLOSURE proves all remaining original developer/attestor host isolation, hostile real-tool denial, live peer authentication, revocation/non-reuse, exact retry, lost-reply/repeated reopen and valid agent reviewer positives on macOS/Linux; (5) ML-PG-ACCEPTANCE separately qualifies the decision and proves old-to-new accepted-ref CAS/restart; then clients and evaluation. The Q24 human-per-ticket verdict route is superseded prospectively, not re-admitted from the old custody packet. No refusal-only or synthetic success substitutes for these positives. Each stage needs its own admission, exact-candidate review and host evidence. Q25's independently reviewed ordering is authoritative here, but **not** proof of this protected spec-selection/seal design, implementation or host readiness; the stopped packet-binding code cannot resume until this correction itself is independently reviewed. For nonempty required check sets, v1's empty-only packet must refuse: before broker's positive, independently admit a closed complete check-set packet schema rather than misrepresent passing checks as `policy_empty`.

## Atomicity, read-set and recovery

Issue is one transaction: authenticated original canonical request/intent (UID, principal, project, role, operation, target, request ID, expected authorization revision), current enrollment/assignment and mutation authorization, staged reserve/create/claim/issue, domain launch event, exact packet response bytes/digest/reference and command result commit or all roll back. The response is mandatory for each productive issue; no alternate packet/submit/settlement path consumes issued authority without it. Core checks full request identity/content at first issue; completed exact retry checks current outcome-read authorization first, then original UID/principal/project/intent/full request bytes and result binding, **not** the stale mutation revision, consumed claim or active-attempt pointer. Request-ID-only result read uses the same stored intent/snapshot binding. Fresh ID on the same operation target conflicts; it does not launch again. Revoked or reassigned callers do not get old bytes merely because the old result exists.

Protected read-set/CAS includes: current identity enrollment, revocation generation and project/role assignment revision; original intent/request digest and target uniqueness; admitted spec revision/content including unique consuming-entry key and matching domain ticket/attempt/execution revision; contract ID/revision/content and selected entry, producer-role membership and consumer-role equality and policy ID/revision/history/check set/independence; control/ledger/reservation/lease and effect/claim/epoch/request/predecessor revisions; attempt closure and **attempt producer-set generation/index (including absence/phantoms)**, every producer effect/claim/execution/inbox attribution and their historical policy revisions; seal uniqueness/status and exact frozen binding/import receipt/domain freeze revision for reviewer issue. Submission CAS covers the same producer-set index, submitted claim and absence of another seal. Import CAS covers seal, unique candidate binding, repository/base and frozen domain transition. Read keys for set membership and historical rows must be declared to the protected read-set checker, not merely loaded inside a transaction; transaction serialization plus generation increments on every relevant creation/attribution/freeze prevent insertion between query and commit. If inbox actor can change after seal, either prohibit it for sealed producers or version and recheck it on reviewer issue; preserve issuer membership even if later settlement changes. On policy/contract/spec change between read and issue, CAS refuses; sealed candidates do not silently migrate to new rules. On import and consumer issue Core compares the selected key and original contract revision in the spec, seal, import binding and effect; at reopen it reconstructs the identical selection from the original authenticated admission, not from today's policy or current attempt. Restart/replay revalidates authenticated admissions and immutable historical versions, original intent, transaction bundle/result, full response reconstruction, complete producer-set enumeration from append-only effect/claim/execution creation and attribution history through the seal-cut sequence (not today's mutable effect status), generation increments and subsequent seal prohibition, all domain/protected bijections, one-to-one frozen import binding and historical check-set emptiness; current authorization is separately evaluated on *each* result exposure. Missing history, conflicting versions, incomplete backfilled legacy claims, corruption or unknown protocol version fences productive issues/packet reads (and keeps unresolved holds); never fabricate a snapshot from today's facts or treat absence as non-delivery. A recorded digest verifies bytes, not semantic correctness.

## Traces and attacks (design assertions, not executed tests)

- Developer: protected operator admission of S(T/A) selects the consuming `reviewer` entry of V **before** D1 is issued. D1's authenticated `developer` role is in that entry's sole producer-role set; D1's own no-candidate/`submit` entry controls its packet. D1/P1 under claim C1 yields null candidate, empty exclusions, pinned S/P/V fields and `return={command:submit,ticket_id:T}`. D1 submission seals `{D1}` under S's selected key before import, without claiming its Git object valid. No selected consumer means no producer issue/seal; no caller may invent one at submission.
- **Conditional future multi-producer trace, unavailable as a first-implementation positive:** S(T/A) selects V's `reviewer` entry; D1/P1 has a separately proved claim/request/epoch/operation-bound terminal non-start and D2/P2 then issues/submits under the *same retained attempt* only if an operator-approved evidence source, channel-quiescence proof, atomic domain handoff and R4a predecessor/ordinal rule have independently been reviewed and implemented. Today no such proof source is selected: D1 instead remains unknown with holds and excludes D2; an issuer exit, expiry, operator assertion or recovered packet cannot advance this trace. Once that independent gate exists, exhaustive seal set `{D1,D2}` and issuers `{P1,P2}` bind imported F. Reviewer R/P3 receives sorted `[D1,D2]`, exclusions `[P1,P2]`, historical checks/independence and `review`; omission of D1/P1, duplicated D2, sibling-attempt D1, or a sibling reviewer issuer P1 refuses (the last by historical protected independence). A forged Git author P4 is irrelevant. The first implementation's useful-positive reviewer path uses the single-producer D1 seal and verified import instead; it does not claim this conditional multi-producer scenario passed.
- Two-consumer counterexample: admitted X requires `[A]`, Y requires `[A,B]`; S(T/A) immutably selects Y/V before any A or B effect. An authenticated A submission must enumerate A **and** B from protected history or refuse; the caller's X token/list cannot shrink the set. X's later issue against this seal refuses even if X is a valid contract entry; Y's issue must match the complete imported binding. S selecting X instead excludes B as an eligible producer: attempting B's productive issue or seal refuses, rather than silently sealing a Y-style set. Missing S selection, two selected keys, stale contract revision, or role-token substitution all refuse. Role `A`/`B`/`X`/`Y` are opaque policy data, never Core literals.
- Revision race: policy P or contract V changes before seal/issue: stale expected revision refuses. After seal, a change cannot rewrite its provenance or silently make a consumer issue under different rules; v1 requires a newly admitted attempt. A completed packet remains old bytes under current authorized outcome-read access. An omitted nonempty historical check set cannot display `policy_empty`.
- Crash cuts: intent alone may issue once if still authorized; interrupted staging commits nothing; issue committed but reply lost/reopened twice returns identical bytes and one issue, including after claim consumption and later active attempt. Changed request/revision, fresh request ID on the same target, sibling UID/project, revocation or lost read permission refuse; a missing historical snapshot remains unknown/held. Imported F with different seal or altered submission digest never produces a reviewer packet. An unverified object cannot become a verified candidate by issuing R.
- Proposed distinct red controls for implementation: erase S's single selected key (A submission must refuse); replace Y with X in the seal or consumer issue while `[A,B]` exists (must refuse); allow B to issue under X's `[A]` selection (must refuse); remove producer generation CAS (insert D3 during seal); drop a producer or issuer from reconstruction; take sibling attempt or role-token substitution; substitute live policy/checks or change V mid-issue; bypass import-to-seal equality; move snapshot write after issue; skip current access on retry; drop snapshot on reopen. Each must turn a corresponding positive/refusal/reopen assertion red in a focused scratch mutation. These are **not run** in this design ticket.

Compared with the rejected privileged role-specific formatter/API, this adds a finite admitted table, one operator-selected consumer key in the already required immutable spec admission, and fixed generic checks, preserving rule 3 and R3's independently enforcing Core. The repair-plan ordering is separately reviewed at Q25; this packet design still requires its own independent review, operator admission of reference entries/spec selection, authenticated submission and seal, read-set/restart extension, and the later candidate importer. No protected code, tests, host evidence, terminal non-start proof, full gate or FR-08A rebind is supplied here. If the authenticated submission channel, admitted spec or exhaustive historical lineage cannot be implemented, refuse productive issuance; a role-specific callback or controller declaration is not a fallback.
