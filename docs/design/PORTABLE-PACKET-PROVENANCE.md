## Smallest privileged shape

The operator admits one immutable, versioned **finite packet contract** per project through the protected maintenance/admission boundary. An admission is an authenticated, append-only record with project, contract ID/revision, canonical bytes/digest, packet schema version and a closed map from opaque role labels to entries. Exactly one entry per label; no wildcard, default, aliases, implicit predecessor, caller override or change in place. A v1 entry has exactly `mode` (`no_candidate` or `frozen_candidate_all_producers`), `producer_roles` (empty for the first mode; nonempty, unique, ordered canonical labels for the second), `return_command` (one token from the installed finite command vocabulary), and `packet_schema_version=1`. Admission verifies that every producer label is an admitted role, that the role/command pair is admitted for this project's authenticated command endpoint (a packet cannot grant a new command), and that each declared producer role is permitted to produce for the consuming role. The **operator**, not a controller, chooses and reviews those entries and policy revisions. The reference lane admission has the opaque keys `developer` → `(no_candidate, [], submit, 1)` and `reviewer` → `(frozen_candidate_all_producers, [developer], review, 1)`; these strings are data in the admitted record, never new literals/sites in Core. Unknown labels, modes, commands, versions, duplicate JSON keys, extra entry fields or a command without an authorized endpoint refuse admission or issue. A role in an issued effect selects its entry; callers supply no mode, producer selector, binding list, callback, template, path expression or DSL. No runtime formatter runs in Core. The contract is privileged policy data, not a new role-specific Core API: Core has only two fixed generic predicates and one closed packet schema. A revision changes only future issuances and requires explicit compatible revalidation of an already sealed candidate; old response bytes retain their historical revision. No contract admission is itself an execution permission.

For productive issue the fixed verifier reconstructs **every field** of the closed v1 packet, encodes one canonical response, and compares the entire proposed response byte-for-byte (or emits it itself). Exact top-level keys: `schema_version`, `packet_id`, `role`, `ticket_id`, `attempt_id`, `execution_id`, `effect_id`, `request_id`, `claim_id`, `writer_epoch`, `issuer`, `base_revision`, `base_ref`, `title`, `spec_revision_id`, `scope`, `acceptance_criteria`, `checks`, `candidate`, `independence`, `return`. No omitted, extra or duplicate keys at any depth. Schema version is 1; packet ID equals execution ID. Role, ticket/attempt/execution/effect/request/claim IDs, epoch and issuer come from the authenticated original intent, staged protected issue/claim/effect and matching domain execution. Base revision/ref, title, spec revision ID and ordered scope/criteria come from an immutable **operator-admitted spec snapshot** for that ticket/attempt, with the domain ticket/spec required to equal it, not from a free kernel projection or packet request. `checks` is exactly `{"policy_empty":true}` only when the pinned historical protected policy's required check set is actually empty; nonempty/unknown sets refuse v1 rather than print empty (a future nonempty representation needs a separately admitted schema). `independence` has exactly `policy_id`, `policy_revision`, `independent_of_roles`, `excluded_principals`: first three come from the complete historical protected policy entry for the issued role, including ordered role labels. `return` has exactly `command` from the sealed entry and `ticket_id` from the effect. In no-candidate mode `candidate=null` and exclusions `[]`. In all-producers mode `candidate` has exactly `candidate_id` and `producer_execution_ids` from the frozen binding below; exclusions are the sorted unique **full issuer set** of precisely those producer effects. Lists are canonical (producer IDs sorted unique; exclusions sorted unique); reject missing, extra, repeated or reordered values. Historical policy and contract content are checked by revision and authenticated admission, not by present policy or a packet's digest. The issued role cannot select its own check set, excluded issuers or return verb.

## Producer seal before Git import

The authoritative **membership** is a protected, attempt-scoped seal, not a list in `artifact_frozen`, Git history, a candidate-supplied manifest, or a query of the mutable active attempt. Require one authenticated submission through an issued claim, matching its original request/epoch/effect/execution and ticket/attempt. The submission's commit/object name and artifact bytes are merely **UNVERIFIED** inputs. Under one protected transaction, Core enumerates *all* protected effect rows for that exact ticket/attempt whose role is in the consuming entry's `producer_roles`, including previous retries/non-starts; checks each effect's original authenticated issuer and unique execution, its claim/epoch if claimed (or independently proved pre-claim non-start), predecessor and matching domain execution/role/attempt (bijection, with no unmatched domain producer execution or protected producer effect), and the submitting effect's issued claim and authenticated submitting actor. An unclaimed effect without proved non-start or a possible outstanding producer blocks the seal. Do not infer membership from the current active attempt, only successful receipts, or a caller's selected subset. Require at least the submitting execution, its role in the producer-role set, a valid chain, complete protected/domain history and no other unsettled productive producer capable of submitting a competing candidate. Missing claim, ambiguous duplicate execution, inconsistent inbox actor/issuer attribution, conflicting submission, missing admitted spec, or incomplete history refuses, never silently filters a row. The packet exclusion set is all these effects' **authenticated issuers**, conservatively including prior failed producers; preserve their inbox actors separately for protected independence, whose historical pairings may be stricter. Submission issuer attribution is rooted in the peer-authenticated claim (under installed custody), not in a Git author string. Before that authentication is installed, no claim of hostile-caller producer proof is permitted.

Core allocates a unique opaque candidate **binding ID** and atomically seals `(project, ticket, attempt, admitted spec revision/content, policy ID/revision/content, packet contract ID/revision/content, submitting claim/effect/execution/issuer, complete ordered producer execution/effect/issuer triples, attempt producer-set generation and append-only seal-cut sequence, submission request ID/digest, retained unverified submission bytes and object reference/digest)` with the authenticated submission and domain submission event. This record is immutable. Prevent subsequent producer-effect creation or another candidate submission for that attempt after seal; corrections use a new attempt and a new seal. A non-submission or failed transaction seals nothing. The fixed verifier constructs the membership set by its own exhaustive query and records its count/generation, not by checking only the proposed triples. A matching authenticated domain event is required but is not sufficient authority: Core verifies its exact identity/spec/execution linkage against root facts. Core does not certify source bytes, scope, ancestry, hooks or checks here.

Later **ML-PG-CANDIDATE** imports exactly the retained submission bytes under its own independent Git/object/scope/check verification and atomically binds its actual frozen candidate ID, repository/object format, base, commit/tree and trusted import receipt to this exact immutable seal ID and submission digest, with a unique one-to-one relation. It rejects an alternative seal, changed bytes, mismatched base/spec/attempt or double binding. A domain `artifact_frozen` proposal may refer only to that exact bound ID; a protected reviewer issue requires that binding and matching domain freeze, not merely the projection's candidate ID. This is a two-phase authority split: a seal proves *who was involved and what submission was named*, an import proves *what Git object was frozen*; check receipts require the later check authority. Neither phase alone establishes the other. Candidate import can use the seal API without ever issuing/recovering a packet; custody's packet route can issue developer packets now, but **reviewer issue waits for the later verified import**. Thus ML-PG-CANDIDATE does not depend on an already successful reviewer packet, and custody cannot claim full reviewer-packet acceptance before that later capability exists. If the milestone order requires a positive reviewer packet before ML-PG-CANDIDATE, the order must be explicitly revised; never accept a kernel-only freeze to break the cycle.

## Atomicity, read-set and recovery

Issue is one transaction: authenticated original canonical request/intent (UID, principal, project, role, operation, target, request ID, expected authorization revision), current enrollment/assignment and mutation authorization, staged reserve/create/claim/issue, domain launch event, exact packet response bytes/digest/reference and command result commit or all roll back. The response is mandatory for each productive issue; no alternate packet/submit/settlement path consumes issued authority without it. Core checks full request identity/content at first issue; completed exact retry checks current outcome-read authorization first, then original UID/principal/project/intent/full request bytes and result binding, **not** the stale mutation revision, consumed claim or active-attempt pointer. Request-ID-only result read uses the same stored intent/snapshot binding. Fresh ID on the same operation target conflicts; it does not launch again. Revoked or reassigned callers do not get old bytes merely because the old result exists.

Protected read-set/CAS includes: current identity enrollment, revocation generation and project/role assignment revision; original intent/request digest and target uniqueness; admitted spec revision/content and matching domain ticket/attempt/execution revision; contract ID/revision/content and policy ID/revision/history/check set/independence; control/ledger/reservation/lease and effect/claim/epoch/request/predecessor revisions; attempt closure and **attempt producer-set generation/index (including absence/phantoms)**, every producer effect/claim/execution/inbox attribution and their historical policy revisions; seal uniqueness/status and exact frozen binding/import receipt/domain freeze revision for reviewer issue. Submission CAS covers the same producer-set index, submitted claim and absence of another seal. Import CAS covers seal, unique candidate binding, repository/base and frozen domain transition. Read keys for set membership and historical rows must be declared to the protected read-set checker, not merely loaded inside a transaction; transaction serialization plus generation increments on every relevant creation/attribution/freeze prevent insertion between query and commit. If inbox actor can change after seal, either prohibit it for sealed producers or version and recheck it on reviewer issue; preserve issuer membership even if later settlement changes. On policy/contract/spec change between read and issue, CAS refuses; sealed candidates do not silently migrate to new rules. Restart/replay revalidates authenticated admissions and immutable historical versions, original intent, transaction bundle/result, full response reconstruction, complete producer-set enumeration from append-only effect/claim/execution creation and attribution history through the seal-cut sequence (not today's mutable effect status), generation increments and subsequent seal prohibition, all domain/protected bijections, one-to-one frozen import binding and historical check-set emptiness; current authorization is separately evaluated on *each* result exposure. Missing history, conflicting versions, incomplete backfilled legacy claims, corruption or unknown protocol version fences productive issues/packet reads (and keeps unresolved holds); never fabricate a snapshot from today's facts or treat absence as non-delivery. A recorded digest verifies bytes, not semantic correctness.

## Traces and attacks (design assertions, not executed tests)

- Developer: operator's admitted role entry selects no candidate/`submit`. `D1` effect issued by authenticated P1 under claim C1 and spec S/policy P/contract V yields exactly null candidate, empty exclusions, pinned S and P fields and `return={command:submit,ticket_id:T}`. `D1` submission seals set `{D1}` before import, without claiming its Git object valid.
- Multiple producers: same attempt T/A has D1/P1 non-start then D2/P2 issued and submitting (both with authenticated effects/claims/domain executions). Seal's exhaustive set is `{D1,D2}` with issuers `{P1,P2}`; later verified import binds candidate F to **that seal**. Reviewer R/P3 issued against F receives sorted `[D1,D2]`, exclusions `[P1,P2]`, historical checks/independence, and `review`. Missing D1 or P1, duplicated D2, P2-only caller list, D1 from sibling attempt, or a sibling reviewer issuer P1 must refuse (the last by protected independence, including historical pairings). A role-token swap to unknown/other admitted role or `submit` for R cannot choose another entry; effect role, claim assignment and contract key must agree. A forged Git author P4 is irrelevant to producer attribution.
- Revision race: policy P or contract V changes before seal/issue: stale expected revision refuses. After seal, a change cannot rewrite its provenance or silently make a reviewer issue under different rules; explicit reviewed revalidation/re-admission or new attempt is needed. A completed packet remains old bytes under current authorized outcome-read access. An omitted nonempty historical check set cannot display `policy_empty`.
- Crash cuts: intent alone may issue once if still authorized; interrupted staging commits nothing; issue committed but reply lost/reopened twice returns identical bytes and one issue, including after claim consumption and later active attempt. Changed request/revision, fresh request ID on the same target, sibling UID/project, revocation or lost read permission refuse; a missing historical snapshot remains unknown/held. Imported F with different seal or altered submission digest never produces a reviewer packet. An unverified object cannot become a verified candidate by issuing R.
- Proposed distinct red controls for implementation: remove producer generation CAS (insert D3 during seal); drop a producer or issuer from reconstruction; take sibling attempt or role-token substitution; substitute live policy/checks or change V mid-issue; bypass import-to-seal equality; move snapshot write after issue; skip current access on retry; drop snapshot on reopen. Each must turn a corresponding positive/refusal/reopen assertion red in a focused scratch mutation. These are **not run** in this design ticket.

Compared with the rejected privileged role-specific formatter/API, this adds only a finite admitted table and fixed generic checks, preserving rule 3 and R3's independently enforcing Core. It still requires operator admission of the reference entries and independent review of this privileged schema, authenticated submission and seal, read-set/restart extension, and the later candidate importer. No protected code, tests, host evidence, terminal non-start proof, full gate or FR-08A rebind is supplied here. If the authenticated submission channel, admitted spec or exhaustive historical lineage cannot be implemented, refuse productive issuance; a role-specific callback or controller declaration is not a fallback.
