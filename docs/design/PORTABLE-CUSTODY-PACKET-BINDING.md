## Boundary choice

At this base, `AtomicBundle.commit_atomic_bundle/6` stages protected operations and domain commit in one SQLite transaction, then persists a closed result. `Protected.ReadSet` checks protected prestate; `Protected.RestartCheck` revalidates the recorded operations/domain/plan but has no packet result. `ManualLane.Backend.issue/6` commits launch before `packet/3` builds with `WorkPacket.build/3` from today's active attempt/policy; its later `excluding_developers/3` reads issuer subsets separately. Consumption or attempt movement makes rebuilding the original packet unsafe. The prototype's role-specific Core builder and a direct Core call to outside-namespace `Foundry.WorkPacket` both violate the protected boundary.

Use **one** new bounded versioned `packet_result_v1` carrier on a productive single-`issue_claim` launch bundle. A role-specific presentation may prepare the packet outside Core, but the protected verifier **reconstructs every byte's meaning independently** from its fixed generic schema and authoritative facts, then compares the whole proposed canonical response byte-for-byte (or emits the reconstructed bytes). No caller-selected binding list, callback, template/DSL, plugin, unchecked packet, digest-only assertion, post-issue result write, rule-3 allowlist widening or role literal in Core. The only role lookup is the authenticated effect's opaque label into the operator-admitted immutable historical contract entry. The entry chooses one of two built-in modes (`no_candidate`, `frozen_candidate_all_producers`), fixed producer-role labels, one endpoint-authorized return command and packet schema version; no wildcard/default, caller override or migration of a sealed attempt. Core's predicates are fixed; a candidate cannot install the contract. Contract admission must reject unauthorized role/return pairs, duplicate/unknown entries or inconsistent consumer selection. The protected operator-admitted ticket/attempt spec names exactly one consuming entry and contract revision **before** any candidate producer issue. A producer's own entry controls its packet; the spec's selected entry controls eligibility to produce and the later consumer issue. An absent/ambiguous selection refuses candidate-producing issue, submission and seal. No untrusted workflow projection selects the future consumer.

A root-owned role-specific formatter outside Core is not a substitute: without separate privileged attestation and review its role/return and complete issuer set are not independently verified by Core; having it run as a callback under the transaction inverts the boundary. A digest of its output only preserves a potentially wrong packet. The finite admitted contract plus fixed predicates is the smallest reviewed *design* path. A new role-specific privileged Core API is neither necessary nor authorized. If implementation cannot produce the authenticated admissions, exhaustive seal/import linkage and historical reconstruction below, refuse productive issue and seek another design review rather than weakening the test or fabricating a result.

## Exact transaction and field proof

For first issue, the local endpoint supplies peer-authenticated UID (not a JSON claim); protected current enrollment maps it permanently to principal/role/project and verifies non-revocation, current assignment and mutation permission at the request's expected authorization revision. The durable intent binds original UID, principal, project, role, request ID, target execution, original **complete canonical request bytes** (including version, operation, ticket and expected revision) and digest. Core reads that intent, current enrollment/assignment revisions and target uniqueness under its protected read-set/CAS **inside the issuance transaction**. Compare authenticated actor to effect issuer and the original intent; reject sibling UID/project, altered body or stale first-issue revision. The caller cannot name a different effect/claim to hijack the intent. Check command ID, one reserve/create/claim/issue sequence, current protected policy/control/ledger, lease/reservation/predecessor guards, and the matching domain launch event and execution projection. Stage issue and domain writes; build/verify packet; persist canonical original request/response bytes, response digest and immutable result reference tied to intent/command/issued effect/claim/epoch, domain result and bundle result **in the same database transaction**. If any read, fact, encoding, uniqueness, write, bound-domain or verifier check fails, roll back claim/effect/reservation/domain/snapshot together. A rejected/no-issue bundle has no successful packet. A successful newly issued claim has exactly one durable result; all packet, result, submit and settlement/consumption routes enforce this barrier before exposing or using it. An intent alone is not an issued claim. A derivative custody cache can only reference the committed result, never define it.

For the **closed v1 response** (canonical JSON plus its specified newline, exact keys and bounds), Core reconstructs all nested and top-level fields, rejects duplicate JSON keys, extras, missing fields, incompatible types, repeated or reordered list members and noncanonical bytes:

| Output | Independently authoritative source and required equality |
|---|---|
| `schema_version`, `packet_id`, `role`, `ticket_id`, `attempt_id`, `execution_id`, `effect_id`, `request_id`, `claim_id`, `writer_epoch`, `issuer` | Version exactly 1; packet ID equals staged execution ID. Authenticated intent/actor, admitted spec's ticket/attempt, staged protected issue's effect/claim/epoch and matching domain execution must agree on each identifier and opaque role. Never take a packet ID or issuer from caller text. |
| `base_revision`, `base_ref`, `title`, `spec_revision_id`, ordered `scope`, ordered `acceptance_criteria` | Complete immutable **operator-admitted** ticket/attempt spec snapshot at its pinned revision/content; issued domain ticket/spec must equal that admission, not supply authority itself. Reject missing spec history, changed base, reordered criteria/scope or competing admission. |
| `checks` | Complete historical protected policy required check set for the issued role/revision. V1 admits *only* an actually empty set and emits exactly `{"policy_empty":true}`; nonempty, unavailable or unknown set refuses. A nonempty required-check broker positive must first have its own separately admitted **complete** packet schema, contract, policy and fresh attempt admission; never print empty for passing checks or retrofit a sealed v1 attempt. |
| `independence` | Exactly `policy_id`, `policy_revision`, ordered `independent_of_roles` from the complete pinned protected policy entry for the issued role, and sorted unique `excluded_principals`. Protected independence/issuer checks still run independently; the packet display cannot relax them. |
| `candidate` and `excluded_principals` | `no_candidate`: null and `[]`. `frozen_candidate_all_producers`: the exact verified candidate bound one-to-one to the immutable seal ID and original retained submission digest/bytes, with domain freeze equality; `candidate_id` and sorted distinct **entire** sealed producer execution ID list, exclusions the sorted distinct entire set of authenticated issuers of those effects (including eligible prior failed producers). Producer **membership** is sealed under authenticated submitting claim/request/epoch/actor before Git import: Core exhaustively enumerates all protected effects for the exact attempt whose roles belong to the *spec-selected future consuming entry's* producer set and checks the complete domain-execution bijection, original issuer attribution, claimed epochs or independently proved terminal non-start, predecessor chain, submission target, generation and absence/phantom keys. An outstanding/unknown producer, missing historical claim or unmatched domain execution blocks sealing. The unique seal retains the submitting unverified bytes/object name, full producer effect/execution/issuer triples, admitted spec/policy/contract revisions, seal-cut sequence and producer-set generation. It bars any later producer effect or competing submission on that attempt. Before import a legitimate **foundation developer** packet uses its own `no_candidate` entry, null candidate/empty exclusions and `submit`; the seal does not claim valid Git objects or checks. The later CANDIDATE importer independently validates exactly the retained bytes and Git/base/scope/checks and binds one actual frozen candidate and trusted import/check receipts one-to-one to the seal, without needing a reviewer packet or full custody closure. A **reviewer/consumer** packet is issuable only **after** verified import, matching domain freeze, spec-selected consuming entry, issuer independence and the required trusted check facts; its candidate/producers/exclusions and `review` return are reconstructed from pinned data. Broker agent-reviewer positive additionally requires the distinct-UID no-execution attestor boundary and, if policy checks are nonempty, the separately admitted nonempty-check schema. The software reference's labels `developer` and `reviewer` occur only in admitted data/controller presentation; Core compares opaque labels, fixed modes and authoritative effects, never hard-codes those names.

Read-set/CAS must include current UID enrollment/revocation and project/role assignment generation, original intent/target uniqueness, admitted spec/unique consumer selection and contract ID/revision/content, historical protected policy/check/independence revision, control/ledger/reservation/lease, effect/claim/epoch/predecessor, domain ticket/attempt/execution revision and closure, and exhaustive attempt producer-index generation **including absence keys**. For sealing include all original producer effect/claim/domain-execution/inbox attribution rows and no-other-seal generation. For later consumer issue include immutable seal, unique verified import/candidate binding, trusted check receipts and domain freeze revision. Increment generation for any relevant creation, attribution or freeze; transaction serialization alone does not excuse omitted read dependencies. If inbox actor attribution can change after sealing, forbid it for sealed records or version and recheck it before consumer issue. CAS refuses changed admission/policy/contract before issue; no v1 attempt migration. Historical committed results remain pinned to their original revisions, not live policy or active attempt.

## Recovery and refusal

For exact `packet` retry, check **current** peer enrollment, non-revocation, project and outcome-read authorization *before looking up or exposing bytes*. Compare UID/principal/project and full incoming canonical request bytes (old expected revision included) to the original intent and packet reference, then serve the stored original canonical response bytes; `result` with only request ID authenticates current reader and verifies the stored intent/snapshot association. Neither repeats `launch` nor requires the old claim still issued, the old mutation revision still current, or the old attempt/candidate still active. An authorized original actor reassigned to a later candidate may read its old outcome if its current project/outcome-read permission survives; replacement/sibling principal or revoked UID cannot. Fresh request ID against the same already-issued execution/target conflicts, never derives a new effect from today's active pointer. Changed request, expected revision or project refuses. Claim consumption, active-attempt movement, repeated ready reopen and lost reply do not alter original bytes, effects, reservations or ordinals.

`Protected.RestartCheck` must accept an exact extended bundle envelope/result shape and reconstruct the full response against **historical** authenticated intent, original enrollment/admission/revisions, command/operation/domain result, protected spec/policy/contract/claim/epoch, exhaustive append-only producer history through the seal cut, immutable seal/import and check provenance, and canonical bytes/digest/ref; today's mutable active attempt, policy or claim status are not reconstruction inputs. Current enrollment is checked separately on every read. Missing/corrupt/conflicting **new-protocol** snapshot or missing reconstruction history fences Gateway readiness or, if narrowly isolatable with proof, *all* productive issue/packet-consuming routes for affected authority; it never returns success. A classified pre-protocol issued claim without provable original snapshot remains pending/unknown with holds and successor exclusion where unresolved: never backfill from live WorkPacket or infer non-delivery. Revoked issuers require separate operator reconciliation. Terminal non-start D1→D2 needs independently reviewed exact non-delivery/channel-quiescence evidence and typed atomic R4a handoff; until then unknown retains holds and D2 is prohibited. Packet recovery is not non-start proof.

| Design cut / assertion | Distinct proposed scratch red control (not run) |
|---|---|
| Intent only: no claim; authorized first retry may issue once. Revoke/reassign/stale first-issue revision refuses. | Remove enrollment/assignment CAS; a fresh revoked/reassigned issue wrongly succeeds. |
| Protected stage, domain failure or snapshot failure: entire issue rolls back, no exposed/consumed claim. | Move snapshot to a post-launch write or remove issue barrier; an issued-without-result case appears. |
| Committed issue/reply lost, reopen twice, then consume claim/move attempt: exact bytes and one effect/claim/reservation/ordinal. | Substitute current WorkPacket or require current active attempt; original result changes/disappears. |
| Sealed single producer, verified import: later consumer gets exact candidate/issuer exclusion; sibling/omitted producer or unverified import refuses. | Drop producer index generation, omit an issuer, or bypass import-to-seal equality; exhaustive-set/binding assertion fails. |
| Selected consumer X allows `[A]`, Y allows `[A,B]`: spec selects Y before A issues; cannot seal only A if B issued; X cannot consume Y seal. | Trust caller's X selector or selected subset; omission or wrong consumer is admitted. |
| Nonempty historical policy, changed return action, extra response key: v1 refuses. | Treat digest/present policy/caller-selected bindings as authority; an incomplete or wrong response passes. |
| Revoked/sibling read or changed old request: refuse; missing old snapshot holds/fences, never rebuilds. | Skip current access or restart validation; bytes leak or corrupt result reads as success. |

No code, tests, host install, full gate, FR-08A rebind or operator non-start proof is claimed. Implementation requires a separately admitted exact-candidate review and real isolated-process, useful-positive, restart and scratch-red evidence at the Q25 foundation/import/broker/closure stages. This document changes neither the suspended prototype nor C9.
