## Choice and limits

The human now chooses an autonomous software-factory **first** milestone: an independently assigned agent reviewer may submit a protected verdict, and a protected writer may promote an ordinary accepted candidate without a human action on every ticket. This supersedes dogfood Q23's human-verdict default **only after this amendment is independently approved and its implementation passes the gates below**. Until then the old route remains disabled and no recorded manual-lane review or model output becomes protected acceptance. A reviewer verdict is an attributable judgment, **not** proof that code is correct; only protected validation of scope, trusted checks, reviewer independence, current policy and exact candidate produces acceptance. No autonomous root/policy upgrade, deployment, general launch, model-spend enforcement or external `main`/PR promotion is added. R3's operator maintenance of verifier/launcher/auth/activation root and R4a's unknown/retry exclusions remain intact.

## Review authority separated from executable tools

Provision a dedicated non-admin, non-login **review-only OS identity per reviewer principal**, permanently enrolled for that role and project, separate from developer, check-worker, operator and `foundry-svc` identities. A root/operator-installed, pinned **review broker** launches a pinned reviewer model process under that identity with no shell, subprocess, arbitrary file/network tool, candidate test/hook/build tool, ambient extension or plugin discovery, inherited privileged descriptor, writable candidate checkout, service cookie or generic MCP/CLI tool access. It receives only bounded immutable source/diff, trusted check receipts, spec and policy snapshots through a closed read-only broker interface; source, agent instructions, notes and check output are untrusted data, never instructions or permission. The broker's only protected write is a structured verdict/notes-bytes request for the **issued reviewer assignment** through the authenticated local authority socket. It cannot supply actor, role, entitlement, check receipt, acceptance or promotion; peer identity, assignment and policy are derived and verified server-side. The reviewer agent chooses approve/correction/reject and reasons, not the route's powers. The broker may read a sealed candidate but **does not run it**. Any needed interactive search or test executes in a different, restricted worker UID with no reviewer credential or inherited authority socket; the broker returns bounded read-only results marked untrusted. If a host/client cannot prove every model-directed executable route is absent from the verdict-bearing process and under that worker identity, disable agent verdict submission there; do not fall back to same-UID shell, a prompt instruction, an extension sandbox claim, or agent-supplied UID. Do not run candidate hooks merely to render a diff. This is reviewer-authority containment, not full provider/network isolation. The current UID-501 desktop and ordinary Pi/Codex/Claude sessions are unsupported protected reviewers.

The service uses the reviewed custody socket's verified peer UID and endpoint identity, closed operation vocabulary and protected enrollment/revocation. Enrollment binds UID to principal/role/project for life; no reassignment of retired developer/check-worker UIDs as reviewer. Check enrollment, revocation, project and outcome-read permission on **every** call, including an existing connection and a cached-result read after restart. A reviewer execution is independent only when its authenticated principal and predecessor lineage are distinct from **every candidate producer** under the pinned policy; different model/session labels alone are not isolation. Agent-to-service review requests contain bytes, never server file paths. The broker is a trusted, root-installed authority component and its binaries/configuration may change only by operator maintenance, not by a reviewed candidate.

## Evidence and ordinary promotion

At operator admission, a versioned, operator-installed policy preauthorizes **eligible ordinary tickets** for exact-ref promotion after protected acceptance. The operator pins allowed project, scope and protected required checks; protected code excludes changes to root/verifier, broker, policy, mandatory gates, protected release/configuration and the authorization rules themselves from this ordinary route. A model cannot select or expand the eligible class, omit checks, grant itself a reviewer assignment or ask for promotion. Unsupported or ambiguous classification holds for operator action. An explicit operator-maintained policy/root upgrade path is separate; even if such source is reviewed, it cannot self-install through this ordinary route.

Admission pins accepted-ref commit/revision, immutable spec content/revision, policy ID/revision and eligible promotion class. Candidate import freezes commit/tree and verifies full admitted-base-to-candidate scope; trusted check receipts pin check ID/definition, toolchain/environment, result and exact candidate commit/tree. Issue a reviewer assignment bound to ticket/attempt/execution/claim, producer lineage, candidate commit/tree, spec/policy revisions and **the complete required check receipt set**. Broker request and durable result bind these same values, authenticated reviewer principal, request ID, canonical content digest, notes digest and verdict. Root revalidates current enrollment, non-revocation, assignment and independence before a new verdict and at acceptance; a changed candidate, check set/result, spec, policy, accepted base or reviewer assignment cannot borrow an earlier approval. After revocation, no new verdict or acceptance may use that review; preserve already issued/possibly delivered work and its holds until evidenced reconciliation. Do not turn a revoked approval into a new review by changing its label.

For an authorized exact request retry after lost reply, check **current** enrollment, revocation, project and outcome-read permission first; then match stored actor, request ID and complete content and return the original durable result, even if its old claim was consumed or revision advanced. Do not rerun old mutation preconditions or create another verdict. Changed content, sibling actor or fresh ID against consumed claim refuses. Restart reloads enrollment and claim/review/result bindings before serving; absent, corrupt or conflicting results remain unknown with holds and no inferred success. Reviewer non-start preserves frozen candidate and checks, closes only proved non-start execution and permits a bounded newly assigned independent reviewer per R4a; possibly delivered or unknown work is **not** a proved non-start. No re-review of mutable source.

The protected acceptance predicate (not a model verdict or display phase) atomically verifies all pinned current facts and records an acceptance ID. For eligible ordinary work, **that** fact authorizes one durable promotion effect without a per-ticket human click. Before issuing it, atomically revalidate policy/spec/acceptance/base/ref revisions and hold a per-project exclusion against dependent changes and promotions through settlement/reconciliation. The fixed protected writer alone updates `refs/foundry/accepted` in the service-owned bare repository by exact old-to-new CAS to the accepted candidate commit/tree; no caller selects ref, target or command. On lost reply/restart, matching verified new commit/tree settles once; matching old permits retry only after the prior issuer/channel cannot still act; third value, missing/corrupt object or uncertain channel stays conflict/unknown with exclusion. A moved accepted base requires revised admission, fresh candidate checks and independent review, not a patch-equivalent cherry-pick. Promotion is accepted-source movement, not deployment or external Git integration.

## Required proof before enablement

Use real root-provisioned **macOS and Linux** process identities (Linux CI needs a separate privileged fixture); synthetic UID inputs, same-user worktrees and mocked broker calls do not prove custody. For each host, exercise: (1) hostile candidate source and test/hook plus a real reviewer-visible tool/search attempt to reach socket, call verdict, alter policy/store/bare ref or execute under reviewer UID: OS/operation refusal and unchanged evidence; (2) a legitimate reviewer agent inspects frozen source through the no-execution broker, returns a bound approval/correction, trusted checks pass, protected acceptance and **one** preauthorized exact CAS promotion succeed; (3) duplicate, sibling, changed candidate/check/policy/spec/assignment, wrong producer or reviewer, revoked UID on open/restarted connection, policy/root-scope candidate, direct ref write and moved-base attempts refuse; (4) lost verdict or CAS reply, broker/service kill at before/after-commit cuts and repeated reopen return the same result or explicit unknown, never a duplicate verdict, ref write, successor or inferred non-start. Inspect actual tool registry, process UID, executable/configuration ownership, inheritance, sockets, sandbox/extension paths and restart state; remove each decisive broker/identity/evidence/CAS guard in a scratch red control and show its corresponding refusal/restart test fails. Include a positive useful task so refusing everything cannot pass. Independent implementation review and trusted checks must precede operator host enablement. A failing or unavailable host remains disabled.

A distinct reviewer OS identity limits credential sharing with candidate-executing routes; it does not make the model semantically independent. Same-provider developer/reviewer models may share training, failure modes or prompt-injection susceptibility. Malicious source or check text can still persuade an agent to approve a defect. Record provider/model lineage and this residual risk; do not call such a verdict human judgment or a security proof. Monitor false approvals, legitimate-work refusals and operator recovery cost in the prospective evaluation.
