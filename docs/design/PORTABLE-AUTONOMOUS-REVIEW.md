## Choice and limits

The human now chooses an autonomous software-factory **first** milestone: an independently assigned agent reviewer may submit a protected verdict, and a protected writer may promote an ordinary accepted candidate without a human action on every ticket. This supersedes dogfood Q23's human-verdict default **only after this entire new base-to-candidate range is independently reviewed and its implementation passes the gates below**. The earlier `cfb2de877992985331e512f90954afbe0bc3c6fe` design-only candidate was approved against older criteria; that approval remains historical, is not integrated and does not approve this role-agnostic correction. Until then the old route remains disabled and no recorded manual-lane review or model output becomes protected acceptance. A workflow reviewer decision is an attributable judgment, **not** proof that code is correct; only protected validation of scope, trusted checks, authenticated independent attestor lineage, current policy and exact candidate produces acceptance. No autonomous root/policy upgrade, deployment, general launch, model-spend enforcement or external `main`/PR promotion is added. R3's operator maintenance of verifier/launcher/auth/activation root and R4a's unknown/retry exclusions remain intact.

## Generic protected authority and no-execution attestor

The protected service does not implement a privileged `reviewer` operation, a reviewer role check, or a second workflow reducer. Its closed, versioned **scoped attestation** operation accepts a bounded decision token and notes bytes for an issued capability. The trusted operator installs a finite policy manifest at admission: for each scoped capability kind it names permitted authenticated principals/UID enrollments, project and assignment lineage constraints, allowed decision tokens, required protected receipt kinds/IDs and exact evidence bindings, and the token(s) qualifying for acceptance. Software workflow names those capabilities and maps them to roles (including `reviewer`), assigns work, presents corrections/rejection, and proposes issuance/acceptance; no role spelling or workflow projection confers a credential. Root permits issuance only under the admitted manifest and its own durable assignment/claim, enrollment, exclusion and lineage facts. Candidate producer lineage comes from authenticated claim-bound submission and immutable Git import; attestor lineage comes from root issuance under operator-admitted standing policy, not an editable workflow assignment; this issuance needs no per-ticket operator click. If a workflow proposes an assignment but no protected authorization attests its producer/decision-maker lineage, root cannot independently verify independence and **must hold**, not infer it from a board or grant a capability. An operator-admitted standing assignment rule or authenticated admission may supply that protected provenance; model-generated role eligibility is never an authorization source.

The verifier's input is one canonical bounded envelope: contract/request ID, project, capability/assignment and predecessor IDs, expected protected revisions, exact candidate commit/tree, admitted base/ref revision, spec content digest/revision, policy ID/revision, ordered complete check receipt IDs/digests, one policy-listed decision token and bounded notes digest/bytes. The server derives the caller from peer credentials and matches all envelope references to its own immutable records; it refuses extra fields, unknown schema/token/evidence kind, unsupported predicate, changed assignment or incomplete bindings. Output is an attributable immutable attestation ID/record or an explicit refusal/unknown, not an acceptance or arbitrary lifecycle transition. The only predicate vocabulary is fixed equality/current-revision, immutable receipt provenance/result, Git full-diff scope/ancestry, enrollment/non-revocation, principal inequality over protected producer lineage, claim uniqueness and pending/exclusion state. Manifest entries select and conjunct these supported checks; they cannot execute code, parse a policy expression, substitute a self-reported check or waive mandatory root checks. Introducing an unsupported evidence source/predicate requires a separately reviewed operator root change, not a new workflow label. Root verifies that the attestor's principal differs from **every** protected candidate producer; a model/session name, claimed assignment, workflow label or notes cannot prove this. Policy chooses which bounded tokens and verified facts constitute qualifying review and eligible ordinary promotion, not Core's role vocabulary. No check receipt or attestation is valid merely because a workflow projects it as complete.

Provision a dedicated non-admin, non-login **attestation-only OS identity per decision principal**, permanently enrolled for its authorized project/capability, separate from producer, check-worker, operator and `foundry-svc` identities. A root/operator-installed pinned **no-execution attestor broker** launches the pinned model under that identity with no shell, subprocess, arbitrary file/network tool, candidate test/hook/build tool, ambient extension/plugin discovery, inherited privileged descriptor, writable candidate checkout, service cookie or generic MCP/CLI tool access. It receives only bounded immutable source/diff and protected check/spec/policy facts through a closed read-only interface; source, instructions, notes and check output are untrusted data. Its only protected write is the scoped attestation envelope over the authenticated authority socket. Broker and protected service derive actor and authority, never accept a model-supplied role/credential or let the broker issue its own capability, check receipt, acceptance or promotion. Any interactive search/test runs under a separate restricted worker UID with no attestation authority and returns bounded untrusted data. If every executable model-directed route cannot be proved outside the attestor identity, disable this route rather than relying on prompt restraint, same-UID shell or extension sandbox assertions. Current UID-501 desktop and ordinary Pi/Codex/Claude sessions cannot attest authoritatively.

The service uses the reviewed custody socket peer UID and endpoint identity, closed operations and protected enrollment/revocation; enrollment is lifetime-bound to principal/project/capability, never recycled into another authority. Check enrollment, revocation, project, capability, assignment and outcome-read permission on **every** call, including open connections and cached-result reads after restart. Broker binaries/configuration are operator-maintained, never candidate-installable. This is attestation-authority containment, not proof of model judgment or full provider/network isolation.

## Evidence and ordinary promotion

At operator admission, a versioned operator-installed finite policy preauthorizes **eligible ordinary tickets** for exact-ref promotion and pins allowed project, full scope, mandatory protected checks, qualifying decision-token mapping and producer/attestor independence rules. The verifier excludes changes to root/verifier, broker, policy, mandatory gates, protected release/configuration and authorization rules from this route. It does not decide whether a workflow calls an actor developer or reviewer; it checks authenticated capability, protected provenance and admitted predicates. Unsupported or ambiguous classification, missing protected lineage or unverified workflow evidence holds for operator action. Model/workflow cannot select or expand the eligible class, omit checks, mint a capability or request a different promotion target. Root/policy maintenance remains operator-only even when source for it was reviewed.

Admission pins accepted-ref commit/revision, immutable spec content/revision, policy ID/revision, decision mapping and eligible promotion class. Candidate import freezes commit/tree and root verifies full admitted-base-to-candidate scope; trusted check receipts pin check ID/definition, toolchain/environment, result and exact candidate commit/tree. Issue an attestor capability against protected ticket/attempt/execution/claim and producer lineage, candidate commit/tree, spec/policy revisions and **the complete required check receipt set**. Broker request and durable result bind those same values plus authenticated attestor principal, request ID, canonical content and notes digests and decision token. Root independently revalidates current enrollment/non-revocation, issued capability, lineage inequality, exact mandatory passing checks and policy-listed qualifying decision at acceptance; the workflow's verdict interpretation and display state are not inputs of authority. A changed candidate, check set/result, spec, policy, accepted base or attestor assignment cannot borrow an earlier attestation. After revocation no new decision or acceptance may use it; outstanding possibly delivered work remains held pending evidenced reconciliation, never re-labelled as a fresh attestation.

For an authorized exact request retry after lost reply, check **current** enrollment, revocation, project and outcome-read permission first; then match stored actor, request ID and complete content and return the original durable result, even if its old claim was consumed or revision advanced. Do not rerun old mutation preconditions or create another attestation. Changed content, sibling actor or fresh ID against consumed claim refuses. Restart reloads enrollment and claim/attestation/result bindings before serving; absent, corrupt or conflicting results remain unknown with holds and no inferred success. Attestor non-start preserves frozen candidate and checks, closes only proved non-start execution and permits a bounded newly authorized independent attestor per R4a; possibly delivered or unknown work is **not** a proved non-start. No re-review of mutable source.

The protected acceptance predicate (not a workflow verdict or display phase) atomically verifies the policy-listed qualifying decision plus all independently verified mandatory pinned facts and records an acceptance ID. For eligible ordinary work, **that** fact authorizes one durable promotion effect without a per-ticket human click. Before issuing it, atomically revalidate policy/spec/acceptance/base/ref revisions and hold a per-project exclusion against dependent changes and promotions through settlement/reconciliation. The fixed protected writer alone updates `refs/foundry/accepted` in the service-owned bare repository by exact old-to-new CAS to the accepted candidate commit/tree; no caller selects ref, target or command. On lost reply/restart, matching verified new commit/tree settles once; matching old permits retry only after the prior issuer/channel cannot still act; third value, missing/corrupt object or uncertain channel stays conflict/unknown with exclusion. A moved accepted base requires revised admission, fresh candidate checks and independent review, not a patch-equivalent cherry-pick. Promotion is accepted-source movement, not deployment or external Git integration.

## Required proof before enablement

Use real root-provisioned **macOS and Linux** process identities (Linux CI needs a separate privileged fixture); synthetic UID inputs, same-user worktrees and mocked broker calls do not prove custody. For each host, exercise: (1) hostile candidate source and test/hook plus a real reviewer-visible tool/search attempt to reach socket, submit a scoped decision, alter policy/store/bare ref or execute under attestor UID: OS/operation refusal and unchanged evidence; (2) a legitimate software-workflow reviewer agent inspects frozen source through the no-execution attestor broker, returns a policy-mapped bound approval/correction, trusted checks pass, protected acceptance and **one** preauthorized exact CAS promotion succeed; (3) duplicate, sibling, changed candidate/check/policy/spec/assignment, wrong producer or attestor, unprotected lineage, unsupported predicate/token, revoked UID on open/restarted connection, policy/root-scope candidate, direct ref write and moved-base attempts refuse; (4) lost attestation or CAS reply, broker/service kill at before/after-commit cuts and repeated reopen return the same result or explicit unknown, never a duplicate attestation, ref write, successor or inferred non-start. Inspect actual tool registry, process UID, executable/configuration ownership, inheritance, sockets, sandbox/extension paths and restart state; remove each decisive broker/identity/evidence/CAS guard in a scratch red control and show its corresponding refusal/restart test fails. Replace the workflow role label and decision display mapping under a separately admitted policy without changing protected code; a valid capability still succeeds, while the old token, unissued capability and workflow-only assignment fail. Include a positive useful task so refusing everything cannot pass. Independent implementation review and trusted checks must precede operator host enablement. A failing or unavailable host remains disabled.

A distinct attestor OS identity limits credential sharing with candidate-executing routes; it does not make the model semantically independent. Same-provider producer/attestor models may share training, failure modes or prompt-injection susceptibility. Malicious source or check text can still persuade an agent to approve a defect. Record provider/model lineage and this residual risk; do not call such a verdict human judgment or a security proof. Monitor false approvals, legitimate-work refusals and operator recovery cost in the prospective evaluation.
