## Verified starting point and choice

Choose the contract's local bare-repository option for the first host. On this macOS host, `id` reports the interactive `raymondluong` UID 501 in the `admin` group; `ps` reports the running `foundry_lane` BEAM under UID 501. The SQLite database, WAL, owner files, notes, release and policy seed are owned by that user; the database and policy seed are mode `0644`. `dscl . -list /Users UniqueID` found no Foundry role account. This is **not** isolated from unrestricted code run by that user. The current Git checkout is likewise writable by that user. The Linux workflow currently runs the gate on `ubuntu-latest` with no custody fixture or role processes ([CI workflow](../../.github/workflows/foundry-ci.yml)). No local or CI protected-custody result has been run.

The code agrees with that observation: [`Server.context/0`](../../lib/foundry/manual_lane/server.ex) returns the in-BEAM protected capability; [`CLI.run/1`](../../lib/foundry/manual_lane/cli.ex) accepts `--principal`; [`Backend`](../../lib/foundry/manual_lane/backend.ex) uses that string as actor; and [`bin/foundry`](../../bin/foundry) invokes the release's general `rpc` evaluator. The Gateway's capability and SQLite single-owner lock protect in-process calls and concurrency, not another process with the same filesystem and Erlang-node access ([durable store](../DURABLE-STORE.md)). FR-15aA's paper inventory did not install accounts or prove this boundary ([FR-15aB](../REPAIR-PLAN.md#fr-15ab--actual-isolation-and-conformance)).

## First-host layout and ownership

An administrator provisions one non-login **`foundry-svc`** OS account, a separate trusted operator login, and one distinct non-admin OS identity for each developer principal and trusted human reviewer. The trusted Foundry process runs solely as `foundry-svc`; it owns the existing Gateway/SQLite connection, policy decisions and the fixed accepted-ref writer. No candidate source, project test, client plugin, or check worker is loaded or executed in that process. The operator provisions an initial policy and `refs/foundry/accepted` from a verified commit before requests are enabled. The source checkout and candidate/check worker live outside the service account. No unrestricted agent may run as the operator, administrator or service UID, or hold `sudo` rights to one of them. OS administrator/root remains trusted and can override this boundary. This slice protects Foundry authority; it does not isolate a provider, tool, network or worker from arbitrary unrelated files.

Install a root-owned, non-client-writable release and service definition. The service account alone owns a private state directory (`0700`): `/Library/Application Support/Foundry/state` on macOS, `/var/lib/foundry` on Linux. It contains the SQLite database, WAL/SHM, owner marker, notes, policy and per-project local **bare** repository (`0700`); state files are `0600` where applicable. Every parent directory must deny untrusted writes and aliases/symlinks; verify owner, mode and path identity on startup before opening the Gateway or Git. The bare repository is never the agent's checkout; it has no shared object directory or alternate that points into an agent-writable tree. Only the service's fixed writer can update `refs/foundry/accepted`; no direct push service, shell command, Git namespace selection or generic ref-update request is exposed. CANDIDATE later owns safe object import and validation; ACCEPTANCE later owns the durable promotion claim and exact old-to-new CAS. Backups and migration need their own operator procedure before production use.

Expose one bounded, versioned, local stream-socket protocol (length-bounded JSON requests; closed operation and field vocabulary). Use `/private/var/run/foundry/authority.sock` on macOS and `/run/foundry/authority.sock` on Linux: root-owned parent (`0755`), service-owned socket directory (`0750`, callers group), socket (`0660`, callers group). The service obtains the peer UID from the accepted connection and maps it to **one configured principal and role**, then authorizes the requested operation for that role and project. A group grants connection only, never a role. Protected enrollment durably binds each provisioned UID to one principal and role for its lifetime; refuse reassignment or reuse, including developer-to-reviewer changes after retirement. Persist revocation in protected authority and check current enrollment and role before **every** operation, including reads, cached request-result lookup and calls on an existing connection; a new mutation also requires its current issued assignment. Revocation invalidates that connection's authority without relying on group changes. Outstanding executions of a revoked principal remain pending/unknown for operator reconciliation with evidence; they are never reassigned. Restart reloads enrollment and revocation before accepting requests. Reject unknown peer identity, self-declared `principal`, role changes, and requests naming another project's assignment. Authenticate the endpoint itself by the administrator-owned parent path and peer service UID; clients refuse a substituted endpoint. No TCP listener, Erlang distribution, release `rpc`, or direct access to the BEAM cookie survives on the protected service. A small platform credential adapter is justified only if the BEAM socket API cannot return verified peer credentials; a claimed UID in JSON is never a substitute. On macOS, Apple's [`getpeereid(3)`](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man3/getpeereid.3.html) reports effective peer UID/GID on a connected UNIX stream socket. On Linux, [`unix(7)`](https://man7.org/linux/man-pages/man7/unix.7.html) documents `SO_PEERCRED` and pathname-socket permissions. The adapter and socket permission behavior require real host tests.

On macOS, the administrator installs a root-owned `/Library/LaunchDaemons` job with `UserName=foundry-svc`, a fixed root-owned executable, and restart policy; `launchd` starts and supervises it, not an agent shell. [Apple's daemon guide](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html) documents the system job location, `UserName`, and `KeepAlive`. On Linux, an administrator installs a systemd system service with `User=foundry-svc` and an owned runtime/state directory; [systemd.exec(5)](https://man7.org/linux/man-pages/man5/systemd.exec.5.html) documents that identity and its `RuntimeDirectory`/`StateDirectory` settings. The service binds its local socket and checks its mode before readiness. The service must restart with the same OS identity and policy, reopen the durable store and reconcile pending authority state before writes. No client can restart it with alternative arguments, code, policy, or state path. `recover` is operator-only and retains the Gateway's evidence requirement.

## Authentication and replay at the API

| Caller | Granted operations | Credential boundary |
|---|---|---|
| Operator | Admit, assign/revoke a principal, install initial policy/ref, recover, later request acceptance/promotion; read status | Dedicated trusted login/account, not shared with candidate or agent shell; peer UID maps to `operator` |
| Developer | Read its assigned packet/status; submit or settle its issued execution | Dedicated non-admin UID mapped to the exact developer principal and project/claim; no operator or reviewer operation |
| Reviewer | Read frozen candidate/check facts; record its own review verdict or settle its issued execution | Separate non-admin UID used only by a trusted human review client; never by an agent or candidate-executing tool |

The first-host credential is the OS login/session, scoped by UID-to-principal mapping and assignment; no bearer token is copied into a prompt, worktree, process environment or packet. Provision and revoke mappings through the trusted operator path; a retired UID is never reassigned or reused. A client secret readable by unrestricted code under the same UID has no isolation value. For this first milestone, a reviewer agent may inspect the frozen candidate and draft notes under a UID with **no reviewer authority**. A separate trusted human reviewer obtains that candidate, the trusted check facts and the draft notes, inspects them, and submits the authoritative verdict from a review-only client under the reviewer UID. That client must not execute candidate code, tests, project hooks, shell tools or agent extensions. The agent's notes transfer as untrusted review material, not a verdict or credential. Agent self-submission is unsupported until a client/tool adapter proves every candidate-executing route uses an identity without reviewer authority. The current shared-admin-UID desktop setup cannot be a protected reviewer route. Codex CLI and Claude Code MCP can each act as external developer clients under their **own** restricted UID, using the same semantic API; the operator and reviewer use separate trusted sessions. Neither client receives operator/reviewer authority. An MCP adapter may translate the same calls but cannot accept a model-supplied role or become a second authority store.

Every mutating call carries contract version, project, `request_id`, expected revisions and an operation-specific bounded body. The service derives actor/principal/role from the peer, never the body. First authenticate the peer and check current enrollment, revocation and permission to read that request's outcome. If the request ID exists, match its authenticated actor, project and complete canonical content (including expected revisions) against the durable record, then return its original result/refusal without rechecking the completed mutation's old revisions, assignment or unconsumed claim. Changed content or a sibling actor refuses; a revoked actor cannot retrieve even its old result. Only a new request checks current assignment, protected revisions and claim preconditions before the existing Gateway write. The durable request record binds authenticated actor, project, complete canonical request digest and result/refusal. An exact retry after restart has **no second effect**; a fresh ID cannot duplicate a consumed claim, review or promotion. Do not treat a socket reconnect, packet text or client-provided label as a fresh identity. Status/read-result resolves an uncertain response for an authorized caller; operator reconciliation handles revoked executions. The protected socket returns packet bytes and accepts bounded review-notes bytes, never caller-selected paths. CLI `packet --out` writes those bytes locally under the caller UID; CLI `review --notes` reads locally and sends bytes. Reject all server-side path-bearing file read/write fields and operations, including the old flag shapes. No generic protected command, arbitrary Git command, or `--checkout` path passed into the trusted process may execute candidate code; reuse the semantic backend only after removing unauthenticated CLI entry points and privileged file I/O. CANDIDATE later owns protected candidate import.

## Executable acceptance before enabling the route

Use actual OS-isolated caller processes, not mocked UID strings. Preserve the current manual lane separately until the protected route passes. A failure in provisioning, peer-credential lookup, socket permissions, owner/path checks, disabled Erlang RPC, or restart recovery leaves protected mutations disabled.

| Caller/process and attempt | Required result |
|---|---|
| Developer UID and hostile project test subprocess: edit SQLite/WAL/owner/notes/policy and bare-repo objects or `refs/foundry/accepted`; access BEAM RPC | OS denial; trusted state and ref unchanged |
| Developer UID: claim reviewer role/verdict, use reviewer packet or copied request; reviewer UID: claim operator or sibling reviewer/developer principal | Auth/assignment refusal, no review or root write |
| Valid developer UID: send old `packet --out` shape naming policy/ref/authority file or a symlink to one; valid reviewer UID: send old `review --notes` shape naming a protected file | Socket rejects paths; protected files unchanged and unread; local CLI flags operate only under caller UID |
| Reviewer agent's real candidate test/hook/shell tool route under a UID without reviewer authority: submit a verdict; trusted human review client under reviewer UID: submit after inspecting candidate, check facts and draft notes | Agent tool denied; human verdict binds to exact candidate and issued reviewer assignment |
| Authorized UID: replay same request after timeout/restart; same ID with altered body or a sibling UID; fresh ID against consumed claim | Original result once, then conflict/refusal; no duplicate event/effect |
| Authorized UID: commit a request that advances its own expected revision or consumes its claim, lose the reply, restart, then retry the identical request ID and content | Original durable result returns despite stale mutation preconditions; revision/claim and event/effect remain changed exactly once |
| Two different enrolled developer UIDs, including CLI and MCP adapters: submit only own assigned claim; operator: valid admission/recovery | Valid scoped calls persist and bind to exact peer-derived principal; sibling submission refuses |
| Revoke a UID while connected, retry its old request after restart, attempt to re-enroll its developer UID as reviewer | All operations including cached results refuse; outstanding execution remains pending/unknown for evidenced operator reconciliation; role reuse refuses |
| Kill/restart service around committed request and pending operation; attempt alternate policy/state path or direct ref write during restart | Reopen/reconcile or remain fenced; no second authority owner or unreviewed ref movement |

Local macOS can inspect present ownership and, **after administrator provisioning**, run the OS-account, peer-credential, hostile-process and restart controls. The present UID-501 lane cannot pass them. Linux CI can run the same isolated-process fixture only after its workflow provisions non-admin test users/service ownership and invokes the fixture outside the ordinary gate; the current workflow has neither step. GitHub documents that hosted Linux VMs permit [passwordless `sudo`](https://docs.github.com/en/actions/reference/runners/github-hosted-runners), but a green job on a single shared UID would still prove nothing. Manual host acceptance must inspect the installed launchd/systemd job, account privilege and group membership, socket/listener inventory, protected path modes, release/RPC exposure, initial policy/ref provenance, and backup/recovery procedure. The macOS administrator must create the accounts, trusted install and launchd job; the CI maintainer must add the Linux fixture. Neither has been done by this design ticket.
